# 岗位 JD 解读与匹配度评估

## JD 的隐藏结构

一份岗位描述看似一段文字，实际包含五个层次的信息，重要性和确定性依次递减：

| 层次 | 内容 | 确定性 |
|---|---|---|
| 硬性门槛 | 学历、专业、毕业时间、工作年限 | 最高，不满足直接筛掉 |
| 核心技能 | 必须掌握的技术栈 | 高，面试重点考察 |
| 加分技能 | "熟悉 xxx 者优先" | 中，影响排序 |
| 职责描述 | 入职后做什么 | 中，决定你的兴趣匹配 |
| 团队介绍 | 业务方向、组织情况 | 低，通常比较模糊 |

读 JD 的第一步是把这五层拆开，而不是通读一遍凭感觉判断。

## 硬性条件怎么判断

硬性条件不满足时，投递的性价比很低，但并非绝对没机会。判断标准是看措辞：

- **"要求"、"必须"**：基本没有余地，不满足建议放弃
- **"优先"、"期望"**：可以尝试，用其他优势弥补
- **"了解"、"接触过"**：门槛很低，大胆投

学历和毕业时间是硬门槛中最硬的。如果 JD 写"2027 届硕士"，而你是 2028 届，通常会被系统直接过滤。

专业限制相对宽松，尤其是 AI 应用类岗位。控制、自动化、电子这类工科专业通常在可接受范围内，但需要你在简历里主动建立专业与岗位的关联。

## 从关键词反推考察重点

JD 里的技术名词不是随便列的，出现频次和位置能反映权重。

**看技术栈的排列顺序。** 排在前面的通常是团队主力技术。例如"熟悉 Python，了解 Java 者优先"，说明是 Python 团队。

**看动词。** "设计"、"优化"、"负责"这类词说明岗位有一定自主性；"参与"、"协助"说明是执行角色。

**看规模词。** "海量数据"、"高并发"、"低延迟"这些词出现，说明工程难度是考察重点。

**看业务词。** "知识库问答"、"智能客服"、"代码生成"这类词决定了你的项目经验是否对口。

把这些词提取出来，和自己简历上的关键词做交集，交集越大匹配度越高。

## 匹配度评估的量化方法

凭感觉判断匹配度容易失真。一个可操作的算法是加权打分：

**必须技能（权重 40%）**：JD 里明确要求的技术，你会多少。全部会得满分，缺一项扣相应比例。

**加分技能（权重 15%）**：写"优先"的技术，会就有分。

**必须条件（权重 15%）**：学历、专业、毕业时间是否满足。

**学历层次（权重 5% 到 15%）**：学历越高或学校越好，得分越高。

**经验匹配（权重 5% 到 10%）**：项目经验与岗位职责的重合度。

**地点匹配（权重 5%）**：城市是否一致。

按这个权重算出来的总分，参考区间是：

- **80 分以上**：高度匹配，重点投递
- **65 到 80 分**：基本匹配，可以投，需要在简历上强化关联
- **50 到 65 分**：勉强匹配，需要有针对性的准备
- **50 分以下**：不建议投，除非有特殊理由

这个算法的价值不是给出精确分数，而是强迫你逐项对照，避免"感觉挺合适"的模糊判断。

## 技能匹配要区分"会"和"用过"

同一个技术，深度差别很大。评估时要区分三档：

- **能讲清原理并做过项目**：算真正掌握
- **跟着教程做过 demo**：算了解，不能算掌握
- **只是看过文档**：不算会

在简历和面试中，把"了解"包装成"掌握"是常见错误。面试官只要追问两层就会暴露，反而扣分。

## 不匹配时的处理策略

**技能缺口小（缺 1 到 2 项加分技能）**：直接投，在简历里强调相邻能力。例如岗位要求 Redis 而你只熟悉内存缓存，可以写"熟悉缓存设计，使用过本地缓存与 TTL 策略"。

**技能缺口中等（缺核心技能）**：考虑用项目补齐。花两周做一个相关的小项目，比硬投效果好。但要注意，临时赶的项目经不起深挖。

**技能缺口大（缺多项核心技能）**：先不投，把它作为下一阶段的学习目标。硬投的结果通常是简历筛选就挂，浪费时间。

**硬性条件不满足**：除非有内推或特殊渠道，否则不建议投。

## 一份 JD 的拆解示例

假设 JD 如下：

> 岗位职责：负责公司知识库问答系统的设计与开发，包括文档解析、检索优化、效果评测。
> 任职要求：计算机相关专业硕士及以上；熟练掌握 Python，熟悉 LangChain 等框架；有 RAG 项目经验者优先；熟悉向量数据库原理；良好的沟通能力。

拆解结果：

- **硬性门槛**：计算机相关专业硕士 → 控制工程是否算"相关"，需要看公司宽严，通常可投
- **核心技能**：Python、LangChain、向量数据库
- **加分技能**：RAG 项目经验
- **职责重点**：文档解析、检索优化、效果评测 → 面试会往这三个方向问
- **隐含要求**：提到"效果评测"，说明团队有工程化意识，要准备评测相关的回答

这个拆解直接给出了准备方向：把 RAG 的三个环节（解析、检索、评测）各准备一个具体做法，面试时主动往这三个方向引。

## 注意事项

**JD 往往滞后于实际需求。** 岗位写的是半年前的模板，实际工作可能有变化。面试时可以通过反问确认。

**同一个岗位在不同渠道的 JD 可能不同。** 官网、招聘平台、内推消息的版本要对比着看，信息更全。

**不要只看技术栈。** 业务方向决定你未来两年做什么，比技术栈更重要。一个用 Python 做风控的岗位和一个用 Python 做推荐的岗位，技术栈相同但成长路径完全不同。
