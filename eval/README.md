# RAG 检索评测

衡量「用户问一个问题，系统能不能召回到应该参考的文档」。这是 RAG 最基础也最容易被忽略的度量——没有它，改切分参数、换 embedding 模型、加不加重排，全都只能靠感觉判断。

## 怎么跑

在项目根目录执行（脚本会自动切到项目根，URL 无关）：

```bash
python eval/run_eval.py                      # 生产配置：纯向量 k=3
python eval/run_eval.py --k 1                # 只取最相关的一条
python eval/run_eval.py --rerank             # 扩大召回 + LLM 重排
python eval/run_eval.py --json out.json      # 保存明细，便于改动前后对比
```

`--rerank` 支持 `--recall-k` 和 `--top-n` 调节召回与保留数量。

## 指标含义

| 指标 | 含义 | 说明 |
|---|---|---|
| Hit@k | top-k 中是否出现期望文档 | 每题只有 1 个期望文档，命中即 1 |
| Recall@k | 期望文档被召回的比例 | 与 Hit@k 在单答案用例上等价 |
| MRR | 第一个正确结果的倒数排名 | 正确排第 1 = 1.0，第 2 = 0.5，越接近 1 越好 |

三个指标一起看的原因：Hit 只看「有没有」，MRR 还看「排得前不前」。只报 Hit 会掩盖「召回到了但排在第三位」的问题。

## 用例怎么加

编辑 `eval/cases.json`，每条包含：

```json
{
  "id": "resume-01",
  "query": "简历要不要放照片",
  "expect": ["01-简历结构与人岗匹配.md"],
  "note": "扣分项里有明确回答"
}
```

`expect` 用文件名（不带路径），因为 `metadata.source` 存的是绝对路径，脚本取 basename 比对。

**写用例的两个原则**：

1. **期望答案必须唯一**。如果一个问题两份文档都能答，这条用例就是坏的。开发过程中踩过两次：`简历写完了接下来该干什么`（可能指简历优化，也可能指投递）、`技术面和 HR 面考察的东西一样吗`（面试流程和行为面文档都相关）。这类用例会导致指标失真，宁可不写或改写问题。
2. **要覆盖难例**。全部写「关键词与标题高度重合」的问题，任何检索方案都能拿 100%，测不出差异。`hard-*` 那几条故意用口语化、场景化的问法。

## 当前基线

23 条用例（4 个主题 + 5 条难例），语料 10 篇约 2.3 万字 / 85 片段：

| 模式 | Hit@3 | MRR |
|---|---|---|
| 纯向量 k=3 | 100.0% | 0.978 |
| 重排 recall=8 → top3 | 100.0% | 0.978 |
| 纯向量 k=1 | 95.7% | 0.957 |
| 重排 recall=8 → top1 | 95.7% | 0.957 |

## 关于重排的结论

重排已实现（`rag/reranker.py`），但**默认关闭**。这是评测得出的结论：

- k=3 时，纯向量已经是 100% / 0.978，重排没有提升空间
- k=1 时两者都是 95.7%，重排修正了「自我评价」一题，但同时把「技术面 vs HR 面」判到了另一份也相关的文档，净效果持平
- 而重排每次问答都要多一次 LLM 调用（约 2 到 3 秒 + 少量 token）

所以当前语料规模下加它是负收益。什么时候值得打开：语料涨到上千片段、top_n 收到 1 到 2 条、或查询普遍很模糊。改 `config/chroma.yml` 的 `rerank_enabled: true` 即可，不需要改代码。

**这个结论本身比指标更有价值**：它说明评测的作用不只是证明「改进了」，也能证明「这个改动现在不该做」。

## 后续可以扩展的方向

- **生成层评测**：现在只测检索，没测「答案是否正确且忠于资料」。可以加 LLM 打分或人工抽检
- **端到端评测**：测 Agent 是否选对了工具、是否调用了 RAG
- **稳定性**：同一问题跑 3 次看结果是否一致
- **用例扩充**：23 条样本偏小，扩到 50 条以上指标才更有统计意义
